# SurrealQL Manifest

A normative harness for any model that authors SurrealQL. It defines **how the model must behave** when designing or translating databases. It is not a tutorial, and it is deliberately **not tied to any specific schema**.

> **Preconditions — read first**
> - **Version:** targets SurrealDB **v3, current line (3.1+)**. All rules assume v3 semantics. Some features behave differently or silently no-op on v2 (e.g. `WITH REFRESH`).
> - **Transport:** authentication and tests run over the HTTP **`/sql`** contract. Do **not** model or promise behaviour that exists only over WebSocket/RPC (e.g. refresh-over-WS).
> - **Experimental capabilities** (`surrealism` / WASM, `files` / buckets) are **OFF**. Do not emit them.
> - **Companion:** this file pairs with `surql-skill`, which holds the worked code examples and the fitness-function scripts. **This file holds the rules; the skill holds the syntax.**

## How to read this document

- **MUST / MUST NOT** are hard rules. A violation is a defect.
- **PREFER** states the default; deviate only with an inline justification comment.
- The model operates in one of two modes, with identical rules in both:
  - **(a) Translate** an existing SQL schema into SurrealQL — the SQL→SurQL map (§17) is the bridge.
  - **(b) Draft** a greenfield SurrealQL database from a description.

---

## 1. North star

1.1 **Strict by default.** SurrealDB's native features *are* the strict path — they move guarantees out of application code and into the engine. Using them is not a convenience; it is how correctness is enforced. The model MUST prefer the native mechanism over any application-level or hand-rolled equivalent.

1.2 **Minimise boilerplate and human intervention.** When more than one valid approach exists, the model MUST choose the one needing the least boilerplate and the least manual upkeep — i.e. the *automatic* mechanism: a computed value over a maintained one, a sequence over hand-numbering, an auto-updating timestamp over a manual touch, an engine constraint over an application check.

1.3 **Two independent dials.** *Graph* is a **modelling** choice; *schemafull* is a **validation** choice. They are orthogonal. A database MUST be graph-first in modelling **and** schemafull in validation at the same time. Graph-ness is never a reason to go schemaless.

---

## 2. Topology & modularity

2.1 **One namespace, one database.** A database MUST live in a single namespace and a single database. Bounded domains are expressed through table naming and comments — never through separate databases. Rationale: namespaces and databases are isolation boundaries that cannot be traversed or joined across; one database keeps the entire dataset in one queryable graph.

2.2 **REVISIT only for hard tenant isolation.** Multiple databases are justified only when strict tenant/data isolation is a hard requirement. This is a one-way door (§19).

2.3 **Canonical pipeline.** Initialisation MUST be ordered **tables → fields → indexes → functions → events → seed**, with numbered files enforcing it. Seed files MUST carry dependency comments wherever one seed depends on another (e.g. an aggregate or computed value that reads a prior seed).

2.4 **Base, then specialise.** PREFER a small generic core (identity, timestamps, shared edges) that domain tables extend, over bespoke per-project schemas.

---

## 3. Schema strictness

3.1 **`SCHEMAFULL` always.** Every table MUST be `SCHEMAFULL`. Schemaless tables are out of the standard.

3.2 **Typed flexibility only.** Variable or heterogeneous data MUST still be validated, via one of:
- **literal / union types** for variable-but-known shapes — the engine validates the discriminated union; or
- **wildcard-typed sub-fields** (`field.* TYPE <a specific type>`) for open maps with a known value type.

3.3 **No untyped escape.** `FLEXIBLE`, `TYPE any`, and an `object` field with no defined sub-fields are MUST NOT. Any genuine need for openness MUST be expressed through §3.2 and carry an inline justification comment.

---

## 4. Identity, types & sequences

4.1 **Native record IDs.** Primary identity MUST be the native record ID (`table:id`) — a meaningful ID where one exists naturally, otherwise `ulid()`. The model MUST NOT define a UUID or serial primary-key field.

4.2 **Native types.** MUST use `decimal` for money and any exact quantity; `datetime` for instants; `duration` for spans; `geometry<…>` for spatial data; typed `object` and `array<T>` for nested data. MUST NOT store structured data as a JSON string. No native IP type exists — store addresses as `string`.

4.3 **Sequences for human codes.** Sequential, human-readable identifiers (order numbers, invoice numbers, reference codes) MUST be generated by `DEFINE SEQUENCE` — never hand-incremented or assembled in application code.

4.4 **Composite IDs are partition keys; prefer a record range over a secondary index for time-ordered or composite access.** When records are addressed by a natural composite key — `weather:[location, ts]`, `event:[tenant, ts]` — the model MUST encode it in the record ID as an array, not in plain fields, and read slices with a **record range** (`SELECT * FROM t:[$k, $lo]..=[$k, $hi]`). The ID is a direct pointer to the data, so a range scans only the matching partition with **no index to define or maintain**; the equivalent `WHERE` over plain fields needs a compound index and still scans more. This is the default access path for time-series, telemetry, and any high-volume append-only table. The ID layout is a one-way door (§19).

---

## 5. Fields & constraints

5.1 **Constraints are assertions.** Enumerations MUST be `ASSERT $value IN [...]` on a `string` field (no separate enum type). Range, format, and value checks MUST be `ASSERT`. Email MUST be `ASSERT string::is_email($value)`. Constraints over the elements of an array MUST use a closure — `ASSERT array::all($value, |$v| $v IN [...])`.

5.2 **Optionality is explicit.** Nullable fields MUST be `option<T>`; everything else is required.

5.3 **Immutability.** Fields that must never change after creation MUST be `READONLY`.

5.4 **Timestamps auto-maintain.** Entity tables MUST carry `created_at` (`DEFAULT time::now()`) and `updated_at` (`VALUE time::now()`, or `DEFAULT ALWAYS`). `updated_at` MUST update automatically on every write — a plain `DEFAULT`, which only sets on create, is a defect.

5.5 **Internationalization.** UI/display strings MUST be modelled as a dedicated `locale_string` table — `key`, `locale`, `value` with `UNIQUE(key, locale)` — resolved through a single `fn::t($key, $locale)` helper that falls back to a default locale (e.g. `'en'`). The model MUST NOT scatter per-language columns (`name_es`, `name_en`, …) across entity tables; the only exception is a small, fixed set of content captions on a single record. A record's preferred language is a `locale` field (`DEFAULT 'en'`).

---

## 6. Relationships

The single most consequential modelling decision. Choose by this rule:

6.1 **Record link — `record<T>`** — for 1:N / N:1 where the link carries no data of its own.

6.2 **Array of links — `array<record<T>>`** — for a small, bounded set with no per-link attributes.

6.3 **Graph edge — `DEFINE TABLE e TYPE RELATION IN A OUT B`** — when the relationship is **many-to-many**, OR **carries its own data**, OR **will be traversed as a graph**. Edge attributes are set via `RELATE … SET …`. A one-edge-per-pair constraint MUST be a `UNIQUE` index on `in, out`.

6.4 **Explicit referential actions.** Every `record<T>` reference MUST declare `REFERENCE ON DELETE REJECT | CASCADE | UNSET`. The model MUST NOT rely on the default (`IGNORE`), which silently leaves dangling references.

6.5 **Self-reference and hierarchy** MUST be modelled as graph edges and traversed — never as a parent-id column with application-side recursion.

6.6 **Anti-patterns (MUST NOT):**
- a junction/join table with two `record<T>` fields for an M:N relationship → use an edge;
- an edge for a simple 1:N with no edge data → use a link.

> Mental model: a link is a pointer, an array is a short list of pointers, an edge is a thing in its own right. The moment a relationship has properties or you want to traverse it, it is a thing — make it an edge.

---

## 7. Derived data

Choose the mechanism by **where the inputs live**:

7.1 **Own-record derivation → `COMPUTED`.** A value that is a pure function of the same record's own fields MUST be a `COMPUTED` field — evaluated at read, never stale, zero maintenance.

7.2 **Aggregate of own children → stored field + `EVENT`.** Counts, sums, and averages over a record's related children MUST be a stored field maintained by a `DEFINE EVENT` on the child table. This keeps the value indexable and cheap to read. Maintain it by the cheapest correct method: **counts and sums incrementally** (`+= 1` / `-= 1`), but **averages and other non-incremental stats by full recompute** (`SELECT math::mean(…), count() … GROUP ALL` then `UPDATE`), since a mean cannot be correctly nudged in place.

7.3 **Value from a separate, volatile table → snapshot or query-time.** A value derived from an independently-changing table (e.g. a converted amount from a rates table) MUST be either:
- **snapshotted** into a plain field at write time when it must be pinned to a moment (transactions, invoices); or
- **computed at query time** via a `fn::` or inline `SELECT` when it is display-only and must stay live.

7.4 **No sub-query inside `COMPUTED`.** The model MUST NOT bury a cross-record or cross-table sub-query in a `COMPUTED` field: it runs per-read per-record, cannot be indexed, and has known evaluation-order pitfalls. If you need to filter or sort on such a value, that is the signal to apply §7.3's snapshot so it collapses to an own-record `COMPUTED` (§7.1).

## 8. Reactive logic

8.1 **Event bodies may be blocks.** A `DEFINE EVENT … THEN` body MAY be a single expression or a multi-statement block (`THEN { LET …; IF …; UPDATE …; CREATE …; }`) — both are valid. PREFER extracting logic into a `DEFINE FUNCTION` (`fn::`) only when it is reused across events or genuinely complex; a self-contained side effect is fine inline.

8.2 **No self-retriggering.** An event MUST NOT issue an `UPDATE` against its own table in a way that re-fires it; fold side effects such as `updated_at` into the triggering event.

8.3 **Functions own reusable read logic and guarded mutations.** A uniqueness guard (e.g. "already related?") MUST be enforced by a `UNIQUE` index, not by an application check.

---

## 9. Authentication, authorization & security

9.1 **Record access is the auth method.** Application users MUST authenticate via `DEFINE ACCESS … TYPE RECORD`, with `crypto::argon2` for password hashing and an explicit `DURATION FOR TOKEN … FOR SESSION …`. The baseline MUST include `WITH REFRESH` for refresh-token support.

9.2 **No session table.** The engine issues and validates tokens; a `sessions` table or equivalent MUST NOT be modelled.

9.3 **System vs record users are separate.** Administrators and operators use **system users** (`DEFINE USER`, RBAC at root/namespace/database level); application end-users use **record access**. MUST NOT conflate them.

9.4 **`AUTHENTICATE` for auth-time checks.** Claim validation and login-attempt logging/throttling SHOULD use the `AUTHENTICATE` clause — it runs once at authentication, not per query.

9.5 **App-orchestrated flows.** Two-factor and password-reset are application-orchestrated; the database only **stores their state** (reset token + expiry, 2FA secret + backup codes as fields) and **validates** it via `fn::`/`AUTHENTICATE`. A database is "auth-complete" only when refresh is present and 2FA / reset / attempt-logging are each either implemented or explicitly deferred.

9.6 **Refresh is HTTP-only.** Refresh tokens flow over the HTTP REST signup/signin path. The model MUST NOT model or promise refresh over WebSocket/RPC.

9.7 **Authorization in the schema.** Access control MUST be expressed as table and field `PERMISSIONS … WHERE $auth…`, never in application code. Apply least privilege: the narrowest role and lowest level that suffices.

9.8 **Injection.** Untrusted input MUST be passed as bound parameters, never string-interpolated into a query.

---

## 10. Search, vectors & realtime

10.1 **Full-text search.** FTS MUST use `DEFINE ANALYZER` + a `FULLTEXT ANALYZER … BM25` index, **one field per index**, queried with the `@@` operator (numbered `@N@` to pair with `search::score(N)` / `search::highlight(…, N)`). The pre-3.0 `SEARCH ANALYZER` spelling MUST NOT be used.

10.2 **Vectors (note, not core).** Vector / semantic search uses `DEFINE INDEX … HNSW` or `… DISKANN`. DiskANN is newly released (SurrealDB 3.1); treat vector search as a **noted, revisit-later** capability — do not adopt it as a default.

10.3 **Realtime — push and pull are distinct mechanisms.** A client watching for changes *as they happen* (subscription) MUST use `LIVE SELECT`. History replay, catch-up after downtime, audit trails, and sync-to-external-system (a consumer pulling *everything since a cursor*, after the fact) MUST use a `CHANGEFEED` on the table or database, read with `SHOW CHANGES … SINCE <datetime|versionstamp>`. The model MUST NOT poll a `LIVE SELECT` for replay, and MUST NOT stand up a hand-rolled audit/change-log table for what a changefeed already records (§18). Auth-state changes can be observed via the SDK's auth subscription.

---

## 11. Views & aggregates

11.1 **Single-source auto-updating aggregate → `DEFINE TABLE x AS SELECT …`.** This is SurrealDB's incrementally-maintained (auto-updating) materialised view. PREFER it for hot single-table aggregates that should read like a table.

11.2 **Joined / cross-table views are not materialised** (single-source limit) — express them as query-time graph **traversal + `FETCH`**, or as `LIVE SELECT` when realtime push is wanted.

---

## 12. Schema evolution (no migration framework)

12.1 **Schema is declarative and idempotent.** Definitions MUST use `OVERWRITE` / `IF NOT EXISTS` so re-running the pipeline always converges to the declared state. The files describe the intended **end-state**, not a history of changes.

12.2 **No migration framework.** There MUST NOT be a versioned migration chain or a version table. If a field must tighten after data exists, edit the definition in place and run a one-shot backfill+validate query, then re-apply.

12.3 **Design for permanence.** Because there is no migration scaffolding, the one-way-door decisions (§19) MUST be settled correctly up front.

---

## 13. API surface

13.1 **Consume the built-in API.** SurrealDB exposes a fixed HTTP API — `/sql`, `/signin`, `/signup`, `/key/:table`, `/graphql`, `/health`, `/version`, `/import`, `/export`, `/rpc`. The model MUST NOT hand-roll a backend/BFF layer to wrap the database; consume the built-in API directly. The official OpenAPI definition (`github.com/surrealdb/openapi`) is the reference.

13.2 **Custom endpoints.** `DEFINE API` is used ONLY to expose locked-down custom endpoints (with middleware), typically alongside denying arbitrary queries for untrusted callers (§14).

---

## 14. Deploy posture (capabilities)

SurrealDB is secure by default; capabilities are the engine-enforced perimeter.

14.1 **Deny, then allow.** Boot with `--deny-all`, then allow only what the schema uses: the specific function families called (e.g. `crypto::argon2`, `string`, `math`, `time`, `type`, `array`) and — only if an `http::*` integration is genuinely required — a scoped `--allow-net host:port`.

14.2 **Keep scripting and network off.** `--deny-scripting` and `--deny-net` (or tightly scoped) unless a specific, justified need exists.

14.3 **Guests are gated.** `--allow-guests` ONLY when a public read surface is intended; it is safe because a guest can still only do what a resource's `PERMISSIONS` clause permits (a `PERMISSIONS NONE` table is invisible). For a public surface, lock it down with `--deny-arbitrary-query` for the guest/record groups plus `DEFINE API`.

14.4 **Experimental off.** Experimental features (`surrealism` / WASM, `files` / buckets) MUST NOT be enabled.

---

## 15. Testing

15.1 **Test the contract.** Tests MUST exercise the HTTP `/sql` contract directly, without an SDK. The HTTP client (curl, xh, Hurl, …) is incidental and interchangeable.

15.2 **No timing hacks.** Assertions on asynchronous effects (events, computed propagation) MUST use retry-with-interval — never fixed sleeps.

---

## 16. Conventions

16.1 **Naming.** `snake_case` for tables and fields; descriptive verb names for edges (e.g. `belongs_to`, `assigned_to`) with consistent direction; the `fn::` namespace for functions; `table_field` for index names.

16.2 **Comments explain *why*, never *what*.**

---

## 17. SQL → SurQL translation map

The bridge for translation mode. Each SQL construct has one canonical SurrealQL replacement:

| SQL / Postgres construct | SurrealQL replacement |
|---|---|
| UUID / serial primary-key column | native record ID (`table:id`, `ulid()`) |
| `CREATE TYPE … AS ENUM` | `ASSERT $value IN [...]` on a `string` field |
| `CHECK (…)` constraint | `ASSERT …` |
| M:N junction table | graph edge (`DEFINE TABLE e TYPE RELATION IN A OUT B`, `RELATE`) |
| `GENERATED ALWAYS AS (…) STORED` | `COMPUTED` field |
| `updated_at` trigger + function | `VALUE time::now()` (or `DEFAULT ALWAYS`) |
| business-rule trigger | `DEFINE EVENT … THEN` (or `ASSERT` with a sub-query) |
| aggregate view over one table | `DEFINE TABLE v AS SELECT … GROUP BY …` |
| join / denormalised view | query-time traversal + `FETCH` (or `LIVE SELECT`) |
| foreign key `ON DELETE` | `REFERENCE ON DELETE REJECT \| CASCADE \| UNSET` |
| `GIN` + `tsvector` full-text | `FULLTEXT ANALYZER … BM25` + `@@` |
| sequence / serial counter | `DEFINE SEQUENCE` |
| `GRANT` / `ROLE` / RLS policy | table & field `PERMISSIONS`; admin via `DEFINE USER` |
| `DEFINE SCOPE` / `DEFINE TOKEN` (old SurrealDB) | `DEFINE ACCESS` (RECORD / JWT) |
| sessions / refresh-token table | `DEFINE ACCESS … WITH REFRESH` (engine-managed) |
| `TIMESTAMP[TZ]` / `NUMERIC(p,s)` | `datetime` / `decimal` |
| `JSONB` | typed `object` / literal-union types |
| `TEXT[]` / array column | `array<T>` |
| extensions (`uuid-ossp`, `pgcrypto`, `pg_trgm`) | built-in (record IDs, `crypto::*`, analyzers) |

---

## 18. Forbidden reflexes

A model translating from SQL trends toward SQL-shaped output. None of the following may appear:

- a UUID / serial primary-key field
- `DEFINE SCOPE` or `DEFINE TOKEN` (removed in 3.0)
- a sessions / refresh-token table
- a `SCHEMALESS` table as a default
- `FLEXIBLE`, `TYPE any`, or an untyped `object` field
- a cross-record / cross-table sub-query inside a `COMPUTED` field
- the `SEARCH ANALYZER` spelling (use `FULLTEXT ANALYZER`)
- reliance on the default `ON DELETE IGNORE`
- a junction / join table for an M:N relationship
- an event that `UPDATE`s its own table and re-fires
- a versioned migration framework or version table
- a hand-rolled backend / BFF layer wrapping the `/sql` API
- a hand-rolled audit / change-log table for what a `CHANGEFEED` already records
- hand-incremented human codes instead of `DEFINE SEQUENCE`
- string-interpolating untrusted input instead of binding parameters

---

## 19. Irreversibility map (one-way doors)

Cheap to get right up front, expensive to change once data and references exist. Settle these at design time:

- **Record-ID scheme** (meaningful vs `ulid()`, and any composite/partition layout for record ranges per §4.4) — every other record and edge points at these IDs, and the partition shape is fixed once data exists.
- **Namespace / database topology** (one vs many) — splitting later severs cross-database traversal.
- **Link vs edge per relationship** — converting one to the other after data exists is a migration.
- **Sequence vs manual codes** — changing the generation scheme renumbers existing records.

---

## 20. Write & error semantics

20.1 **Writes that may be retried MUST be idempotent.** Any write reachable by a retry, a redelivered message, or an at-least-once pipeline MUST produce the same final state whether it runs once or many times. The native tools are: `UPSERT` for create-or-update by id; `DELETE`, which is already idempotent (a second run is a no-op); and `RELATE` made idempotent by the `UNIQUE(in, out)` edge index already required in §6.3. The model MUST NOT express a create-or-update as application-side `IF exists THEN update ELSE create` — that is a single `UPSERT`.

20.2 **`+=` / `-=` are not idempotent.** In-place accumulators (`SET count += 1`, `SET tags += 'x'`) change on every execution, so they MUST NOT sit on a retry-able path; route counters through the §7.2 event-maintained aggregate instead. Relatedly, on a table with a `UNIQUE` index, PREFER `UPSERT` over `UPDATE` for single-record writes — the engine resolves the record through the index with no table scan.

20.3 **Error-handling hierarchy — push the rule as far down as it will go.** Three tiers, in order of preference: **`ASSERT`** on a `DEFINE FIELD` for any permanent invariant (the engine enforces it on every write — the default home for a rule, per §5.1); **`THROW`** for a runtime/business guard inside a query or transaction that a static `ASSERT` cannot express (it aborts and rolls back the surrounding transaction, and may return a structured value); and **`.expect(|$v| …, 'msg')`** (v3.1+) for a *temporary* invariant while debugging a method chain — it clones the value, so the model MUST remove it from hot paths and MUST NOT use it as a permanent rule.

---

## 21. Fitness functions (enforcement)

Rules are enforced two ways; a database is conformant only if both pass:

21.1 **Engine-enforced** — capabilities (§14), table/field `PERMISSIONS`, `ASSERT`, `UNIQUE` indexes, and `REFERENCE` actions. The engine rejects violations at runtime.

21.2 **Lint-enforced** — automated checks (shipped in `surql-skill`) that reject the §18 forbidden reflexes and flag any §3.2 typed-flexibility use lacking a justification comment. These are the harness the authoring model MUST pass before output is accepted.

---

## 22. Scope

22.1 **In scope (v1):** everything above.

22.2 **Out of scope, noted for later:** WASM modules, file buckets, a full GraphQL BFF, multi-tenant sharding, and vector / ANN search as a default (DiskANN / HNSW noted in §10.2).
